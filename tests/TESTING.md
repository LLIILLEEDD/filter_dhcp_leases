# Практическая DHCP-лаборатория

Лаборатория проверяет программу на настоящих ISC DHCP Server и DHCP-клиенте.
Клиент отправляет DHCPDISCOVER, получает DHCPOFFER и DHCPACK; сервер записывает
аренду в отдельный `dhcpd.leases`. Затем запускается текущий
`filter_dhcp_leases.py`, а сценарий проверяет данные, копии и состояние службы.

Это практические интеграционные испытания без Docker, pytest и подмены
`systemctl`. Для запуска нужен Linux с systemd и правами root.
Все команды выполняются из корня клонированного проекта.

## Важное правило текущей программы

Программа выбирает IP, только если его **последняя запись в файле**:

- принадлежит целевой подсети;
- имеет `binding state active`;
- содержит конечную дату окончания;
- имеет остаток **строго больше** `--hours`.

Для выбранного IP удаляется вся история записей. Истёкшие аренды,
`free` и `ends never` не выбираются. Поэтому эксперимент №2 называется
«Активные, истёкшие и повторные аренды»: он подтверждает сохранение истёкших,
а не приписывает программе несуществующую очистку просроченных записей.

Удаление записи сервера не освобождает адрес у клиента. Эксперименты ниже
относятся только к изолированной сети.

## Как устроена сеть

```text
                         namespace сервера
                        dhl-<token>-server
                     настоящий dhcpd, свой PID
                   свой config и dhcpd.leases
                          /             \
         srv0: 10.203.10.1/24           srv1: 10.203.20.1/24
                     |                   |
                  veth-пара           veth-пара
                     |                   |
                 cli0                    cli0
         dhl-<token>-client-a     dhl-<token>-client-b
             настоящий dhclient     настоящий dhclient
```

Network namespace — отдельное сетевое пространство: у него свои интерфейсы,
адреса, маршруты и сокеты. Пара veth работает как виртуальный сетевой кабель:
пакет с одного конца приходит на другой.

Обе veth-пары полностью перемещаются внутрь трёх namespace. Они не соединяются
с физическими интерфейсами, мостом, NAT или сетью хоста. Исходящие маршруты
на хост не добавляются. Пулы адресов: `10.203.10.100–110` и `10.203.20.100–110`.

Network namespace не изолирует файловую систему. Поэтому у каждого процесса
явно заданы собственные `-cf`, `-lf` и `-pf`. Клиент получает отдельный
`-sf`: наш hook назначает только IPv4-адрес на `cli0`, проверяет namespace
и не изменяет DNS, `resolv.conf` или маршруты хоста.

Служба `dhcp-leases-lab-<token>.service` создаётся через `systemd-run`.
Вспомогательная `...-keeper.service` удерживает ссылку на неё, чтобы systemd
не выгрузил временный unit между stop и start. Keeper — завершившийся
`true` с `RemainAfterExit=yes`, отдельного фонового процесса у него нет.
Оба unit временные; файлы unit в `/etc` не создаются и не редактируются.

## Требования и зависимости

Проверенная среда: Ubuntu 24.04, systemd 255, ISC DHCP 4.4.3-P1.
Потребуются:

| Компонент | Пакет Ubuntu/Debian | Назначение |
| --- | --- | --- |
| Python 3.10+ | `python3` | Программа и сценарии на стандартной библиотеке |
| `ip` | `iproute2` | Network namespaces и veth |
| `systemctl`, `systemd-run` | `systemd` | Временный сервер и реальный stop/start |
| `dhcpd` | `isc-dhcp-server` | ISC DHCPv4 Server |
| `dhclient` | `isc-dhcp-client` | Настоящий DHCP-клиент |
| `bash` | `bash` | Команды запуска |

Необязательно: `tcpdump` для ручного просмотра пакетов. Python-зависимостей
из pip нет. Для сетевых операций нужны CAP_NET_ADMIN и CAP_SYS_ADMIN;
для управления системными transient unit нужен доступ к systemd.
Обычно достаточно `sudo` на полноценной Linux-машине или VM.
Root внутри ограниченного контейнера может не иметь нужных возможностей.

Проверка без создания ресурсов:

```bash
bash tests/check.sh
```

Она проверяет команды и PID 1, но не обещает доступность kernel capabilities.
Окончательная проверка привилегий происходит при создании namespace.

### Установка на отдельной учебной машине

Если пакеты ещё не установлены, администратор может поставить их:

```bash
sudo apt-get update
sudo apt-get install --no-install-recommends python3 iproute2 isc-dhcp-server isc-dhcp-client
```

Установка системного пакета — отдельное действие администратора: она создаёт
системные файлы и может выполнять пакетные service-hook. Сами лабораторные
скрипты пакеты не устанавливают и штатной службой не управляют.
На машине с рабочим DHCP используйте уже доступные бинарники либо вариант
с распаковкой ниже, чтобы не устанавливать/обновлять серверный пакет.

### Получение ISC-бинарников без установки сервера в систему

Если `python3`, `ip` и systemd уже есть, Ubuntu-пакеты DHCP можно просто
скачать и распаковать внутри репозитория, без `sudo`:

```bash
mkdir -p tests/.tools/packages
(
  cd tests/.tools/packages
  apt download isc-dhcp-server isc-dhcp-client
  for package in ./*.deb; do
    dpkg-deb --extract "$package" ..
  done
)
bash tests/check.sh
```

Распаковываются пакеты из репозиториев своей версии ОС и архитектуры.
Post-install скрипты не запускаются, системные unit и конфигурация не меняются.
Проверьте библиотеки, если бинарник не запускается:

```bash
ldd tests/.tools/usr/sbin/dhcpd
ldd tests/.tools/usr/sbin/dhclient
```

`not found` означает отсутствующую библиотеку; её устанавливает администратор.
Поиск бинарников: сначала `tests/.tools/usr/sbin/`, затем системный PATH.
Сам вариант скачивания требует доступа к настроенным APT-репозиториям.

## Запуск всех экспериментов

```bash
sudo bash tests/run.sh all
```

Команда создаёт сеть и сервер, выполняет пять сценариев и удаляет сетевые
ресурсы. Сценарии выполняются последовательно; каждый сбрасывает только
лабораторную базу при остановленном лабораторном сервере.
Обычный прогон занимает около минуты; время зависит от DHCP-обмена.

Вывод содержит:

- название и цель эксперимента;
- реальные команды со знаком `$`;
- состояния базы до и после;
- ожидаемый и фактический результат проверок;
- `PASS` только после успешной проверки данных;
- `FAIL` с причиной при несовпадении или ошибке;
- `CLEANUP OK` после подтверждённой очистки.

Код завершения `0` означает, что выбранные сценарии и обязательная очистка
успешны. При ошибке — ненулевой код. После первого FAIL следующие сценарии
не запускаются; отсутствие их результатов не означает PASS.

## Отдельные сценарии

```bash
sudo bash tests/run.sh 01-address
sudo bash tests/run.sh 02-selection
sudo bash tests/run.sh 03-subnet
sudo bash tests/run.sh 04-safety
sudo bash tests/run.sh 05-service-cycle
```

Каждая команда сама подготавливает окружение и очищает его после испытания.
Если окружение создано заранее через `setup.sh`, `run.sh` использует его
и по умолчанию также очищает в конце.

### №1 — получение IP-адреса: 01-address

1. Запустить отдельный dhcpd в серверном namespace.
2. Запустить реальный dhclient в namespace клиента A.
3. Найти в клиентском журнале DISCOVER, OFFER, REQUEST и ACK.
4. Проверить адрес на интерфейсе `cli0`.
5. Найти этот IP с состоянием `active` и будущей датой в серверной базе.
6. Остановить лабораторный сервер и сохранить стабильный снимок.

**PASS:** подтверждены обмен, назначенный адрес и активная запись в базе.
Успешного запуска процесса недостаточно. Полный блок аренды выводится
в терминал; файл `01-server.leases` сохраняется в результатах.

### №2 — активные, истёкшие и повторные аренды: 02-selection

1. Получить двухсуточную аренду в первой подсети.
2. Повторить обмен с тем же MAC/client identifier и получить тот же IP.
3. Другому клиентскому идентификатору выдать восьмисекундную аренду
   через тот же изолированный интерфейс.
4. Остановить клиента через `dhclient -x` без DHCPRELEASE и дождаться
   реального окончания короткой аренды.
5. Остановить сервер, сохранить `02-before.leases` и запустить программу
   с `--hours 24` в режиме отдельного результата.
6. Сравнить каждый оставшийся блок с исходным текстом.

**PASS:** у длинной аренды действительно есть повторные записи;
удалена вся её история, а все блоки истёкшего IP сохранены без изменений.
Состояние последней истёкшей записи может стать `free` — это нормальная
работа самого dhcpd. Момент окончания в любом случае проверяется по UTC.

Настройка `dhcp-cache-threshold 0` в лабораторной конфигурации нужна,
чтобы повторная выдача записывалась сервером, а не обслуживалась из кэша.
Сценарий отдельно проверяет, что история реально появилась.

**Ограничение:** очистку истёкших лиз текущий CLI не реализует.

### №3 — фильтрация по подсети: 03-subnet

Получить аренду клиентом A в `10.203.10.0/24` и клиентом B в
`10.203.20.0/24`. После остановки сервера обработать снимок с целевой
подсетью `10.203.10.0/24`.

**PASS:** IP первой подсети удалён, IP второй остался. Все блоки другой
подсети совпадают с исходными посимвольно и сохраняют порядок.
Записи второй подсети получены от настоящего сервера, а не добавлены вручную.

### №4 — безопасность изменений: 04-safety

Сценарий проверяет:

- Dry-run на снимке с `--apply --manage-service`: байты неизменны,
  журнал, backup и lock-файл не появляются; MainPID службы остаётся прежним.
- Управляемое применение к другому lease-файлу: проверка `-lf` должна
  отклонить операцию до остановки; MainPID и исходные байты не меняются.
- Отдельный результат: исходник сохранён, резервная копия побайтово равна ему,
  выбранный IP отсутствует в результате.
- Повторную обработку: появляется вторая копия, прежняя не перезаписана.
- Совпадение `--input` и `--output`: ожидается отказ, исходник сохранён.
- Незакрытый блок аренды при `--apply`: ожидается отказ до замены
  и создания резервной копии.

**PASS:** выполнены все перечисленные проверки. Для отрицательных запусков
код `1` ожидаем: этот код сам по себе не делает эксперимент неуспешным,
если отказ произошёл правильно и данные сохранились.

Сценарий не моделирует все возможные отказы диска, питания и запуска dhcpd;
он не заявляет о проверке всех ветвей автоматического восстановления.

### №5 — полный цикл обслуживания: 05-service-cycle

1. Получить настоящую аренду и подтвердить активную запись.
2. Запомнить MainPID и InvocationID лабораторной службы.
3. Запустить текущий CLI с `--apply --manage-service` и явными путями
   лабораторных `--dhcpd`, `--dhcp-config` и `--input`.
4. Программа сама останавливает сервер, выполняет проверки `-t` и `-T`,
   создаёт копию, заменяет базу и запускает сервер.
5. Проверить новый MainPID/InvocationID, копию, отсутствие выбранного IP
   и сохранность остальных lease-блоков.
6. Проверить порядок сообщений в журнале: остановка → замена → запуск → успех.
7. Повторно запустить клиента, получить новый DHCPACK, проверить адрес
   интерфейса и новую активную запись сервера.

**PASS:** подтверждён весь цикл, включая DHCPACK после обслуживания.
Просто `active/running` без работающего клиента здесь недостаточно.

Ручной `systemctl start` между обработкой и новым клиентом не выполняется:
повторный запуск сервера обязан сделать сама программа.
В конце сервер останавливается для стабильного финального снимка.

## Где находятся результаты

Краткая сводка последнего **завершённого** запуска без sudo:

```bash
bash tests/results.sh
```

Команда только читает `summary.json`. Она показывает PASS/FAIL/NOT_RUN,
состояние очистки, среду и путь к полному журналу. Каталог одного лишь
`setup.sh` без итогового отчёта при поиске пропускается.

Для конкретного запуска:

```bash
bash tests/results.sh --results tests/results/ИМЯ_КАТАЛОГА_ЗАПУСКА
```

Подставьте имя из строки «Результаты» в выводе лаборатории.
Код `results.sh` — `0` для сохранённого PASS, `1` для FAIL, неизвестного
итога или ошибки чтения. Это просмотр прежнего испытания, а не повторный тест.

Общий PASS выставляется только при выполнении всех **выбранных** сценариев
и отсутствии ошибки. Незапущенные после прерывания сценарии записываются как
NOT_RUN. При `--keep` очистка отмечается как невыполненная; её нужно запустить
самостоятельно. В JSON также сохраняются сведения об ОС, Python, systemd,
ISC dhcpd и SHA-256 обоих основных Python-файлов. Эти сведения помогают
сравнить два прогона.


В начале запуска печатается каталог:

```text
tests/results/YYYYMMDDTHHMMSSZ-<token>/
```

В нём сохраняются:

| Файл | Содержимое |
| --- | --- |
| `console.log` | Команды, ответы, ожидания, фактические проверки, PASS/FAIL и очистка |
| `summary.json` | Общий итог, PASS/FAIL/NOT_RUN, очистка, среда и SHA-256 программы |
| `dhcpd.conf`, `dhcpd.leases` | Конфигурация и последняя база лабораторного сервера |
| `server.log` | Настоящий вывод dhcpd |
| `client-*.log` | Реальные DHCP-обмены |
| `client-*.conf`, `client-*.leases`, `client-*.events` | Параметры клиента, его база и события hook |
| `02-before.leases`, `02-after.leases` | Состояния эксперимента №2 |
| `03-before.leases`, `03-after.leases` | Состояния эксперимента №3 |
| `04-*.log`, `04-backups/` | Защитные проверки и резервные копии |
| `05-live-before.leases` | Снимок до управляемого применения |
| `05-after-filter.leases` | База после обработки, до нового клиента |
| `05-after-new-ack.leases` | База после нового DHCPACK |
| `05-filter.log`, `05-backups/` | Журнал полного цикла и исходная копия |

Снимок `05-live-before` сделан при активном сервере. Точная исходная версия
для замены — резервная копия, которую программа делает после остановки.
На старте dhcpd может переписать служебный заголовок, поэтому после запуска
сравниваются lease-блоки, а не весь файл с заголовком.

Посмотреть последний прогон:

```bash
run=$(find tests/results -mindepth 1 -maxdepth 1 -type d | sort | tail -n 1)
printf '%s\n' "$run"
sudo cat "$run/summary.json"
sudo less "$run/console.log"
sudo cat "$run/02-before.leases"
sudo cat "$run/02-after.leases"
sudo diff -u "$run/02-before.leases" "$run/02-after.leases"
sudo cat "$run/05-filter.log"
sudo ls -l "$run/05-backups/"
```

После отдельного сценария файлов других экспериментов не будет.
`diff` возвращает `1` при найденных различиях; здесь это ожидаемо.
Некоторые базы и копии имеют права `0600`, поэтому для просмотра нужен `sudo`.
Имена каталогов и даты в арендах меняются при каждом реальном запуске.

## Ручной просмотр запущенной среды

Только подготовить лабораторию:

```bash
sudo bash tests/setup.sh
sudo bash tests/status.sh
```

Вывод status содержит случайные имена namespace, службу и каталог файлов.
Для команд ниже можно получить их из состояния без копирования вручную:

```bash
ns=$(sudo python3 -c 'import json; print(json.load(open("tests/.lab-state.json"))["namespaces"]["server"]["name"])')
unit=$(sudo python3 -c 'import json; print("dhcp-leases-lab-" + json.load(open("tests/.lab-state.json"))["token"] + ".service")')
run=$(sudo python3 -c 'import json; print(json.load(open("tests/.lab-state.json"))["directory"])')
sudo ip -n "$ns" address
sudo systemctl status "$unit" --no-pager
sudo cat "$run/dhcpd.leases"
```

Чтобы получить аренду и оставить сетевую среду для осмотра:

```bash
sudo bash tests/run.sh 01-address --keep
sudo bash tests/status.sh
```

У сценария №1 сервер в конце остановлен для снимка. Namespace и временные
unit сохраняются; если нужен сервер для ручного наблюдения, его можно
запустить по имени из состояния:

```bash
sudo systemctl start "$unit"
```

`--keep` действует только после успеха. При ошибке выполняется очистка.
Если запуск без `--keep` уже завершился, файла состояния не будет.

Для ручного просмотра пакетов на сохранённой лаборатории можно установить
`tcpdump` и запустить в отдельном терминале:

```bash
sudo ip netns exec "$ns" tcpdump -ni srv0 -vv 'udp port 67 or udp port 68'
```

Остановите tcpdump через Ctrl+C перед cleanup: незнакомые процессы
лаборатория автоматически не убивает и при их наличии откажется удалять
namespace. Для новой серии демонстраций используйте `run.sh`.

## Очистка

```bash
sudo bash tests/cleanup.sh
```

Удаляются только зарегистрированные процессы, временные службы, namespace
и veth конкретного запуска. Если собственный временный unit остался
в состоянии `failed`, его отказ сбрасывается после проверки принадлежности,
чтобы systemd мог выгрузить unit. Журналы испытания сохраняются.
Команда повторяемая: при отсутствии состояния она сообщает,
что зарегистрированной лаборатории нет.

Очистка проверяет маркер временной службы, namespace, бинарник клиента,
параметры процесса и время его создания. Нет `killall`/`pkill dhcpd`,
остановки `isc-dhcp-server.service` или массового удаления namespace.
Сеть хоста сравнивается с исходным состоянием; отличие вызывает ошибку,
а не ложный CLEANUP OK.

Снимки и журналы остаются для анализа, даже после FAIL. Они не являются
активными сетевыми ресурсами. Чтобы убрать и результаты, сначала завершите
cleanup, проверьте абсолютный путь и удалите только `tests/results/`:

```bash
sudo bash tests/cleanup.sh
realpath tests/results
sudo rm -r -- tests/results
```

Не удаляйте `.lab-state.json` вручную при работающем сервере: он нужен
для определения принадлежащих лаборатории ресурсов. Пустой `.lab.lock`
после выхода нормален: блокировка держится открытым дескриптором, не наличием
файла. Состояние и результаты исключены из Git.

Обычная ошибка, Ctrl+C и SIGTERM запускают очистку. SIGKILL, перезапуск ОС
или потеря питания не позволяют выполнить завершающий Python-код.
После прерывания проверьте `status.sh` и вызовите `cleanup.sh`.
Если принадлежность ресурса не подтверждена, скрипт откажется управлять им
и сообщит причину; это требует ручного осмотра, а не массового убийства процессов.

## Файлы примеров и структура tests/

```text
tests/
  README.md / TESTING.md / VERIFIED.md
  run.sh / setup.sh / cleanup.sh / status.sh / check.sh / results.sh
  dhcp_lab.py
  config/
    dhcpd.conf
    dhclient.conf
  scripts/
    dhclient-hook.sh
  fixtures/
    selection-input.leases
    selection-expected.leases
  results/                 локальные артефакты; не включаются в Git
```

Bash-файлы — короткие точки входа. Последовательности, ожидания и проверки
написаны в `dhcp_lab.py` на стандартной библиотеке Python; pytest не нужен.
Основные модули проекта не подменяются и не изменяются.

Примеры `fixtures/` синтетические и предназначены для чтения правила
выбора без запущенного сервера; результаты реальных экспериментов ими
не подменяются:

```bash
python3 filter_dhcp_leases.py \
  --input tests/fixtures/selection-input.leases \
  --subnet 10.203.10.0/24 \
  --check-date "2026/08/18 10:20:00" \
  --hours 24 --dry-run --verbose
```

В примере выбран только `10.203.10.100`; удаляются обе его записи.
Истёкший `10.203.10.101`, свободный `10.203.10.102` и адрес другой подсети
сохраняются. `selection-expected.leases` показывает ожидаемый результат.

## Возможные проблемы

| Сообщение / симптом | Что проверить |
| --- | --- |
| Нужен sudo / Operation not permitted | Права root, CAP_NET_ADMIN и CAP_SYS_ADMIN; ограничения среды |
| PID 1 должен быть systemd | Используйте Linux/VM с работающим systemd; подмена systemctl не используется |
| Не найдены dhcpd/dhclient | Пакеты или локальная распаковка в tests/.tools |
| Permission denied при запуске бинарника | Проект на исполняемой Linux FS; noexec, SELinux или другие политики |
| Нет DHCPACK | Смотрите server.log и client-*.log конкретного запуска |
| Лаборатория уже существует | status.sh; завершите предыдущий запуск или cleanup.sh |
| Namespace содержит процессы | Остановите ручной tcpdump/оболочку; cleanup не убивает неизвестные PID |
| Не удалось проверить сеть хоста | Сравните результаты; сеть могла измениться и внешним процессом |

Для воспроизводимости бинарники и клиентский hook копируются в приватный
`bin/` каталога запуска с правами root/0700. Поэтому hook работает даже
после ZIP/Windows-копирования, потерявшего executable bit; менять права
исходных файлов не требуется. Это позволяет использовать явный лабораторный
исполняемый путь и не менять системные AppArmor-профили, привязанные к
`/usr/sbin/dhcpd`/`dhclient`. Глобальные политики не отключаются.
Если исполнение из каталога проекта запрещено вашей политикой, используйте
подходящую Linux VM; скрипты не меняют SELinux/AppArmor и параметры монтирования.
