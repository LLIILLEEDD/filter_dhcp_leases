# Учебный гайд по текущему проекту

Этот документ объясняет текущие `filter_dhcp_leases.py` и
`dhcp_service_manager.py`: что делает программа, как читать её код
и зачем нужны проверки вокруг изменения файла. Новые конструкции Python
объясняются по ходу.

Команды выполняются в Bash, например в Ubuntu внутри WSL, из корня проекта.
Для первых упражнений не нужны root, установленный dhcpd или работающая
служба: достаточно Python 3.10+ и синтетического примера из проекта.

## 1. Какую задачу решает программа

DHCP-сервер выдаёт клиентам IP-адреса на ограниченное время — аренду,
или lease. В базе ISC DHCP могут находиться несколько записей одного IP:
его история меняется, а новые записи добавляются в файл.

Программа читает базу, определяет последнюю запись каждого IP,
выбирает адреса по условию и формирует текст без записей этих адресов.
Затем она либо показывает план, либо сохраняет результат.

Текущее условие выбора одновременно требует:

1. IP входит в `--subnet`.
2. Последняя запись имеет `binding state active`.
3. Есть конечная дата окончания аренды: `never` не подходит.
4. До окончания осталось строго больше `--hours`.

Например, для порога 24 часа:

| Последняя запись IP | Будет выбран? |
| --- | --- |
| Нужная подсеть, `active`, осталось 25 часов | Да |
| Нужная подсеть, `active`, осталось ровно 24 часа | Нет |
| Нужная подсеть, `active`, аренда уже закончилась | Нет |
| Нужная подсеть, `free`, осталось 48 часов | Нет |
| Нужная подсеть, `active`, `ends never` | Нет |
| Другая подсеть, `active`, осталось 48 часов | Нет |

**Это удаление выбранных активных аренд, а не очистка просроченных записей.**
Удаление записи не отправляет клиенту команду освободить IP. Поэтому учебные
опыты выполняй на примере или в изолированной лаборатории.

## 3. Первый запуск: получить план

```bash
python3 filter_dhcp_leases.py \
  --input archive/tests/fixtures/demo.leases \
  --subnet 10.201.90.0/24 \
  --check-date "2026/08/18 10:20:00" \
  --dry-run --verbose
```

Здесь `python3` — интерпретатор, следующий аргумент — файл программы.
Обратная косая черта в конце строки продолжает команду Bash; после неё
не должно быть пробела. Вся команда может быть записана одной строкой.

- `--input` задаёт файл для чтения.
- `--subnet` ограничивает выборку подсетью.
- `--check-date` фиксирует момент сравнения в UTC.
- `--dry-run` показывает расчёт без записи, блокировки и внешних команд.
- `--verbose` добавляет в таблицу IP подсети, которые не будут удалены.

Ожидается 12 исходных блоков, 3 выбранных IP и 8 оставшихся блоков.
Число удаляемых блоков равно 4, а выбранных IP — 3: у одного из выбранных
адресов несколько записей. Разница между блоком и IP здесь существенна.

Дата фиксирована специально: без неё программа использует текущее UTC,
и результат на том же примере со временем изменится.

Полная справка:

```bash
python3 filter_dhcp_leases.py --help
```

## 4. Откуда начинается выполнение

В конце главного файла находится:

```python
if __name__ == "__main__":
    sys.exit(main())
```

При запуске файла напрямую Python присваивает `__name__` значение
`"__main__"`. Условие выполняется, вызывается `main()`, а возвращённое
целое число становится кодом завершения процесса.

При импорте из теста `__name__` содержит имя модуля. Определения функций
загружаются, но этот вызов `main()` пропускается. Поэтому тест может
вызвать одну нужную функцию, не выполняя весь сценарий.

Python сначала выполняет строки модуля сверху вниз: импорты, константы,
определения функций и класса. Тело функции выполняется при её вызове.
Поэтому функция, объявленная выше, может вызывать функцию, объявленную ниже:
к моменту запуска `main()` нужные определения уже существуют.

## 5. Маршрут выполнения от main()

Сначала прочитай `main()`, затем переходи к функциям, которые она вызывает.
Ниже схема основных этапов; это объяснение, а не исполняемый код.

```text
main()
  parse_arguments()                       аргументы и их проверка
  определить момент сравнения в UTC
  configure_logging()                     терминал и файловый журнал
  with service_session(...) as transaction:
    [в управляемом режиме: блокировка, проверки, остановка службы]
    validate_paths() / проверка ссылок
    source_signature() + read_file()       исходные метаданные и текст
    ensure_source_unchanged()              исходник не изменился при чтении
    extract_lease_blocks()                 текст -> список блоков
    get_latest_leases()                    блоки -> последняя запись каждого IP
    find_leases_to_delete()                записи -> выбранные IP
    build_filtered_content()              исходный текст -> новый текст
    verify_result()                       проверить оставшиеся блоки
    print_report()                        показать план
    если dry-run: print_outcome(), вернуть 0
    если apply: apply_safely()
    иначе: save_filtered_file()           копия исходника и отдельный результат
    [при выходе: запустить и проверить управляемую службу]
  print_outcome()                          подтвердить итог
  вернуть 0
  при обрабатываемой ошибке: журнал и код 1
  finally: close_logging_handlers()      закрыть обработчики журнала
```

Без `--manage-service` контекст `service_session()` не управляет службой.
С `--dry-run` он тоже ничего не запускает. Отчёт печатается до применения,
а успешный итог обычного запуска — после завершения записи и возврата службы.

## 6. Аргументы, пути и аннотации типов

`parse_arguments()` использует стандартную библиотеку `argparse`.
Она разбирает строку запуска и возвращает `argparse.Namespace` — объект
с атрибутами `args.input`, `args.subnet`, `args.dry_run` и другими.

Параметры преобразуются в удобные типы ещё до обработки базы:

| Значение | Тип в программе | Зачем |
| --- | --- | --- |
| `args.input` | `pathlib.Path` | Чтение, проверка и построение путей |
| `args.subnet` | `ipaddress.IPv4Network` | Проверка принадлежности IP подсети |
| `args.hours` | `int` | Числовое сравнение времени |
| `args.check_date` | `datetime.datetime` или `None` | Заданный момент либо выбор текущего времени |
| `args.dry_run` | `bool` | Включён ли режим просмотра |

`parse_subnet()`, `parse_check_date()` и `parse_hours()` проверяют значения.
Например, `--hours 0` отклоняется, а `--manage-service` требует `--apply`.
Ошибки аргументов завершаются кодом `2` до основной обработки.

В определении

```python
def read_file(file_path: pathlib.Path) -> str:
```

`: pathlib.Path` описывает ожидаемый тип параметра, а `-> str` — тип
возвращаемого значения. `-> None` означает, что полезное значение не
возвращается. Запись `datetime.datetime | None` означает один из двух вариантов.
Аннотации помогают человеку, IDE и анализаторам; сами по себе они
не проверяют типы при каждом вызове.

Путь `./filter_dhcp_leases.log` отсчитывается от каталога терминала.
Запуск скрипта по абсолютному пути не меняет этот каталог.
На сервере явные абсолютные пути уменьшают путаницу.

## 7. Как текст превращается в данные

### Чтение и поиск блоков

`read_file()` возвращает весь файл одной строкой `str`. Параметр
`newline=""` сохраняет исходные переводы строк, включая Windows CRLF.

`extract_lease_blocks()` проходит по символам, следит за вложенностью
фигурных скобок и учитывает строки в кавычках и комментарии.
Скобка внутри строки или комментария не должна завершать блок аренды.
Незавершённый блок приводит к ошибке вместо записи сомнительного результата.

Это не полный синтаксический анализатор всех возможностей dhcpd:
он извлекает блоки, а `parse_lease()` получает нужные поля регулярными
выражениями. В управляемом режиме дополнительно используется проверка dhcpd.

### Разбор записи

Например, из блока

```text
lease 10.201.90.100 {
  ends 4 2026/08/20 10:20:00;
  binding state active;
}
```

`parse_lease()` получает словарь примерно такого вида:

```python
{
    "ip": "10.201.90.100",
    "ends": "2026/08/20 10:20:00",
    "state": "active",
    "active": True,
}
```

Цифра перед датой — день недели в формате базы; в строке `ends`,
которую возвращает функция, остаются дата и время.
Недостающие поля представлены `None`; неизвестное состояние не становится `active`.

### Последняя запись IP

`get_latest_leases()` проходит по блокам в порядке файла и выполняет:

```python
latest[ip] = lease_data
```

Если ключ IP уже был в словаре, значение заменяется. После прохода
остаётся последняя встретившаяся запись. Это не поиск максимальной даты
`ends`: решает именно порядок записей в файле.

Проверка IPv4 выполняется и для старых записей, даже если ниже есть
более новая запись того же адреса.

## 8. Как выбираются IP и собирается результат

`find_leases_to_delete()` перебирает последние записи и вызывает
`should_delete()` для каждой. Та проверяет подсеть, состояние и время.

Временная цепочка:

```text
строка ends -> parse_end_date() -> datetime в UTC
дата окончания - момент проверки -> timedelta
timedelta > timedelta(hours=args.hours) -> True или False
```

`never` или отсутствующая дата дают `None`; такой адрес не выбирается.
Оператор `>` объясняет, почему ровно 24 часа при пороге 24 не подходят.

В `main()` есть выражение:

```python
ips_to_delete = {lease["ip"] for lease in selected_leases}
```

Это множество (`set`) уникальных IP. Проверка `ip in ips_to_delete`
позволяет быстро определить, надо ли удалять очередной блок.

`build_filtered_content()` снова использует исходный текст и все блоки.
Для выбранного IP она убирает **всю историю**, а не только последнюю запись.
Для остальных адресов сохраняет исходный текст блоков. Если удаляемый блок
занимает отдельные строки, убирает также его отступ и завершающий перевод
строки, чтобы не оставлять по пустой строке на каждый удалённый блок.
Существующие разделители между другими записями не очищаются глобально.

`verify_result()` повторно разбирает новый текст и сравнивает оставшиеся
блоки с ожидаемыми: содержимое и порядок должны совпасть.
Проверка выполняется ещё до записи на диск.

## 9. Отчёт и logging: зачем два способа вывода

`print_report()` показывает человеку параметры, сводку и таблицу.
`print_outcome()` сообщает итог: просмотр без записи или подтверждённое
сохранение. Отметка удаления в таблице означает план, а не доказанную запись.

`logging` нужен для истории запуска: когда выполнялась программа,
с какими параметрами, какие IP выбрала и где произошла ошибка.

`configure_logging()` создаёт один logger и два обработчика:

| Обработчик | Что получает |
| --- | --- |
| Терминальный `StreamHandler` | `WARNING` и выше; краткие сообщения |
| Файловый `FileHandler` | `INFO` и выше; время UTC и подробности ошибки |

В dry-run файловый обработчик не создаётся. Поэтому даже сообщение
`logger.info(...)` не приводит к появлению файла журнала.

Отдельный класс нужен для изменения оформления терминальных ошибок:

```python
class ConsoleFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        return record.getMessage()
```

Это наследование: берём класс библиотеки и переопределяем метод `format()`.
Возвращается только сообщение. Обычный `logging.Formatter`, даже с шаблоном
`"%(message)s"`, может дополнительно присоединить traceback при
`logger.exception()`. Поэтому одного короткого шаблона недостаточно.
Файловый обработчик сохраняет traceback, терминальный его не показывает.
Уровень `WARNING` ограничивает сообщения отдельно от форматирования.

Строка с тройными кавычками сразу после объявления функции или класса —
docstring, документация объекта. Обычный комментарий начинается с `#`.
Docstring доступен через `help()` и атрибут `__doc__`.

## 10. Резервная копия и безопасная замена

### create_backup()

Функция создаёт каталог копий при необходимости, формирует имя вида
`demo.leases.20261017_120000.a1b2c3d4.bak`, копирует исходные байты,
синхронизирует файл и сравнивает содержимое с источником.
Время в имени — UTC; пример имени условный.

`open("xb")` означает создание нового двоичного файла. Если имя уже
существует, возникает `FileExistsError`; программа пробует другой суффикс.
Поэтому старые копии не перезаписываются даже при совпадении имени.
При ошибке незавершённая копия удаляется.

Сама `create_backup()` не принимает параметр dry-run: главный сценарий
просто не вызывает её в этом режиме. Это пример распределения обязанностей.

### apply_safely()

Открыть рабочую базу через `"w"` означало бы сразу обнулить её содержимое.
Вместо этого `apply_safely()` готовит отдельный временный файл в том же каталоге:

1. Проверяет исходник и запоминает его метаданные.
2. Записывает новый текст во временный файл.
3. Переносит обычные права и, на Linux, владельца и группу.
4. Выполняет `flush()` и `os.fsync()`.
5. Читает временный файл обратно и проверяет результат.
6. В управляемом режиме вызывает проверку `dhcpd -T`.
7. Проверяет неизменность исходника, создаёт и проверяет его копию.
8. Ещё раз проверяет исходник и выполняет `os.replace()`.
9. На Linux синхронизирует каталог.

`flush()` передаёт данные из буфера Python операционной системе,
`fsync()` запрашивает их сохранение на устройстве. `os.replace()`
атомарно меняет имя файла: другие процессы видят прежний файл либо новый,
а не наполовину записанный результат. Временный файл рядом с исходником
позволяет выполнять замену в пределах одной файловой системы.

Атомарность не гарантирует работоспособность службы или восстановление
после любого отказа питания. Для этого нужны дополнительные проверки.

`source_signature()` собирает метаданные: устройство, inode, размер,
времена и права. `ensure_source_unchanged()` сверяет их и исходные байты,
чтобы обнаружить изменения после начала анализа. Это защита от обнаруженных
изменений, а не блокировка любого стороннего писателя.

Режим отдельного `--output` реализован в `save_filtered_file()`:
проверка неизменности исходника, его резервная копия, обычная запись
результата и проверка чтением. Атомарная замена относится к `--apply`.
Функция получает пути, текст, исходные байты и метаданные явно — без
дополнительного объекта, который пришлось бы отдельно изучать.

## 11. Как работает with service_session()

В главном сценарии:

```python
with service_session(args, logger, create_backup) as transaction:
    # Здесь выполняются чтение, анализ и сохранение базы.
    ...
```

`with` использует контекстный менеджер: действия при входе, выполнение
вложенного блока и действия при выходе. Знакомый пример —
`with open(...) as file`, который закрывает файл при выходе.

В `service_session()` декоратор `@contextlib.contextmanager`
позволяет описать этот механизм через `yield`:

```text
код до yield       подготовка и остановка службы
yield transaction  управление переходит внутрь with в main()
код после yield    запуск службы после успешной обработки
except             обработка ошибки и попытка восстановления
```

`yield` здесь не завершает весь сценарий: функция приостанавливается,
передаёт значение в `transaction` и продолжает работу при выходе из `with`.
Исключение из вложенного блока попадает в контекстный менеджер.

Без управления службой или при dry-run функция выдаёт `None` и выходит
без подготовки сервера. В управляемом режиме она передаёт словарь состояния:

| Ключ | Зачем нужен |
| --- | --- |
| `replaced` | Произошла ли уже замена рабочей базы |
| `backup` | Путь проверенной резервной копии |
| `original` | Исходные байты для проверки восстановления |
| `stat` | Первоначальные метаданные файла |

Здесь transaction — обычный словарь. Это не транзакция СУБД: успешный
откат зависит от возможности остановить службу, записать файл и запустить её.

Параметр `create_backup` — переданная функция: её можно вызвать из модуля
службы без обратного импорта главного модуля. Аналогично `lease_validator`
в `apply_safely()` — необязательная функция проверки временного файла.
Короткая `lambda path: ...` в `main()` связывает эту проверку с `args` и logger.

## 12. Что проверяет модуль службы

| Функция | Назначение |
| --- | --- |
| `validate_service_environment()` | Проверки Linux/root, путей и доступности systemctl до остановки |
| `run_command()` | Запуск внешней команды, тайм-аут, запись ответа в журнал |
| `service_state()` | Получение состояния и MainPID через `systemctl show` |
| `check_process_binding()` | Проверка бинарника процесса и его параметров `-cf`/`-lf` |
| `validate_config()` | Проверка конфигурации: `dhcpd -4 -t` |
| `validate_lease_file()` | Проверка базы: `dhcpd -4 -T` |
| `stop_service()` | Остановка и подтверждение отсутствия MainPID |
| `start_service()` | Запуск и повторная проверка процесса |
| `service_lock()` | Блокировка параллельных управляемых запусков |
| `restore_original()` | Восстановление исходной базы через временный файл |
| `recover_service()` | Остановка при необходимости, откат базы и возврат службы после ошибки |
| `sync_directory()` | Синхронизация изменений каталога |
| `service_session()` | Общая последовательность и обработка отказов |

Важно различать `-t` и `-T`: первая проверяет конфигурацию, вторая — базу
лиз с выбранной конфигурацией. Проверка `-T` не обслуживает клиентов,
но может создавать собственные временные файлы.

`subprocess.run()` получает список аргументов без shell. Поэтому оболочка
не интерпретирует части команды как свои операторы. Тайм-аут относится
к каждой команде, а не ко всей программе целиком.

Перед остановкой проверяется `/proc/MainPID/exe` и командная строка процесса.
Это связывает выбранную службу с конкретными бинарником, конфигурацией
и базой. Одного похожего имени службы для этого недостаточно.

Блокировка использует `fcntl.flock()` и отдельный файл
`.dhcpd.leases.dhcp-filter.lock`. Он сохраняется после выхода, но сама
блокировка снимается при закрытии дескриптора. Наличие файла не означает,
что программа сейчас работает. Удаление файла при выходе могло бы создать
гонку, когда разные запуски блокируют разные inode под одинаковым именем.

## 13. Что происходит при ошибке

`raise` сообщает об ошибке, `except` перехватывает её, а `finally`
выполняет завершающие действия независимо от обычного успеха или исключения.

В `main()` обрабатываются, например, ошибки чтения, формата и управления
службой. `logger.exception()` записывает причину с traceback; функция
возвращает `1`. В `finally` функция `close_logging_handlers()` закрывает
обработчики журнала. Она же вызывается перед перенастройкой logger.

В управляемом применении `service_session()` перехватывает отказ и вызывает
`recover_service()` под всё ещё удерживаемой блокировкой.
Восстановление зависит от этапа:

- До замены исходник остаётся прежним; после ошибки в защищённой части
  выполняется попытка вернуть службу.
- После замены сначала подтверждается остановка, затем выполняется попытка
  сохранить диагностическую копию и восстановить исходную базу.
  После восстановления программа пробует запустить службу.
- Если восстановление не удалось, сообщение содержит явное указание
  на отказ восстановления и путь к резервной копии.

Даже успешный откат не превращает исходную операцию в успех: код остаётся `1`.
Ошибки ранних проверок до остановки не требуют запускать заново службу,
которую программа ещё не останавливала.

В модуле службы есть перехват `BaseException`: он позволяет попытаться
восстановить состояние и при прерывании вроде Ctrl+C. Это специальное
решение для участка, где служба могла быть остановлена. В обычном коде
такой широкий перехват часто мешает корректно завершить программу.
SIGKILL или выключение WSL не дают выполнить Python-код восстановления.

В Bash код последней команды можно посмотреть сразу после её выполнения:

```bash
echo $?
```

Для обычного успеха и dry-run ожидается `0`, для обрабатываемой ошибки — `1`,
для неверных аргументов — `2`. Прерывания и необработанные исключения
могут завершаться иначе.

## 14. Практика на синтетической базе

### Упражнение 1: объяснить таблицу

Выполни команду из раздела 3. Найди выбранные IP и объясни, почему
остальные строки не выбраны. Затем убери `--verbose` и сравни таблицу.
Правило выбора не изменится, изменится только подробность отчёта.

### Упражнение 2: изменить порог

Повтори dry-run с `--hours 1`, затем с `--hours 1000`.
Предскажи, какой вариант выберет больше адресов. При одинаковой дате
и подсети увеличение порога не должно добавлять выбранные IP.

### Упражнение 3: сохранить результат отдельно

```bash
python3 filter_dhcp_leases.py \
  --input archive/tests/fixtures/demo.leases \
  --output ./demo.filtered.leases \
  --subnet 10.201.90.0/24 \
  --check-date "2026/08/18 10:20:00" \
  --backup-dir ./backups
```

Посмотри результат, копию в `backups/` и `filter_dhcp_leases.log`.
Исходный пример должен остаться прежним. Если повторить команду,
результат перезапишется, а резервная копия получит новое имя.

### Упражнение 4: попробовать замену учебной копии

Сначала создай отдельную копию тестового файла:

```bash
cp archive/tests/fixtures/demo.leases ./practice.leases
python3 filter_dhcp_leases.py \
  --input ./practice.leases \
  --subnet 10.201.90.0/24 \
  --check-date "2026/08/18 10:20:00" \
  --backup-dir ./backups \
  --apply
```

Это ручной режим без настоящего сервера. Он подходит для учебной копии,
которую никто больше не изменяет. Сравни `practice.leases` и её резервную
копию: у результата 8 блоков, у копии исходника — 12.

### Упражнение 5: получить понятные ошибки

Сначала передай `--hours 0`. Затем попробуй одновременно `--apply`
и `--output ./another.leases`. Объясни, почему `argparse` отклоняет
оба запуска до обработки базы.

Отдельно попробуй отсутствующий `--input` с `--dry-run`:
это уже ошибка обработки файла с кодом `1`, а не ошибка синтаксиса аргументов.

## 15. Как читать и запускать тесты

Из корня проекта:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest discover -s archive/tests -p "test_*.py" -v
```

`unittest` — стандартная библиотека тестирования, `discover` находит
тестовые файлы в заданном каталоге. `-v` показывает имена проверок.
`-B` отключает запись кэша для основного интерпретатора,
а переменная `PYTHONDONTWRITEBYTECODE=1` передаёт это правило и дочерним
Python-процессам CLI-тестов.

Начни с тестов фильтрации: исходный текст → вызов функции → сравнение
ожидаемого результата. Затем читай проверки службы. В них внешние команды
подменяются: тест задаёт ответ `systemctl`, проверяет реакцию программы
и порядок вызовов без настоящей остановки DHCP.

Такая подмена называется mock. Она помогает воспроизвести редкие ошибки,
например отказ запуска после замены. Успех этих тестов не доказывает,
что реальный сервер выдаёт адреса: для этого нужна лаборатория и клиент.

## 17. Как читать код после рефакторинга

Основной алгоритм остаётся в `main()`. Разбор текста, выбор IP и проверка
результата идут последовательно; их условия не менялись.
Часть действий вынесена в функции с отдельной практической задачей:

| Функция | Когда открывать её код |
| --- | --- |
| `close_logging_handlers()` | Если разбираешь закрытие файлов журнала; она используется при настройке и завершении |
| `save_filtered_file()` | Если изучаешь режим отдельного результата: копия, запись и проверка |
| `validate_service_environment()` | Если программа отказывается управлять службой из-за окружения или путей |
| `recover_service()` | Если изучаешь действия после ошибки остановки, замены или запуска |

`service_session()` сохраняет общую последовательность. Предварительные
проверки выполняются до остановки, а проверка работающего процесса и
конфигурации — уже под блокировкой. Перенос функции не должен переносить
эту границу безопасности.

В `apply_safely()` аргументов много, потому что нужны разные исходные данные:
текст результата, прежние байты, метаданные, исходные блоки и выбранные IP.
При вызове в `main()` имена указаны явно:

```python
backup_path = apply_safely(
    input_path=args.input,
    new_content=new_content,
    blocks=blocks,
    ips_to_delete=ips_to_delete,
    original=original,
    signature=signature,
    backup_dir=args.backup_dir,
    logger=logger,
    # Далее — уже существующие параметры внешней проверки и восстановления.
)
```

Это сокращённый фрагмент для чтения; полный вызов находится в `main()`.
Запись `original=original` означает: параметру `original` передаётся
значение одноимённой локальной переменной. Новых словарей или классов
для упаковки параметров нет.

Расчёт ширины таблицы теперь использует обычные вложенные циклы:
начальная ширина равна длине заголовка, затем каждое значение может её
увеличить. Формат самой таблицы сохранился.

В ответе `systemctl show` строки вида `ActiveState=active` явно разделяются
на имя и значение. Аргументы из `/proc/PID/cmdline` разделяются нулевыми
байтами: путь с пробелом должен остаться одним аргументом.

Синхронизацию каталога при применении и восстановлении выполняет одна
`sync_directory()`. Отметка `transaction["replaced"] = True` остаётся
сразу после `os.replace()`: если следующий `fsync()` завершится ошибкой,
программа уже обязана знать, что нужно восстановить исходный файл.

По этой причине добавлена одна автоматическая проверка такого отказа:
всего теперь 68 проверок — прежние 67 и одна новая. Эта проверка моделирует
ошибку синхронизации каталога; реальные DHCP-обмены проверяет лаборатория.

Число строк в `main()` не является целью: именованные аргументы занимают
больше места, зато помогают увидеть назначение каждого значения.
Разбор скобок, атомарная замена, `with/yield` и обработка отказов остались:
их сложность связана с форматом базы и безопасностью работы сервера.

Рекомендуемый порядок чтения: `main()` → аргументы → разбор блоков → выбор
IP → сборка результата → нужный способ сохранения → `service_session()`
и восстановление. После каждого этапа найди соответствующий тест и попробуй
объяснить его своими словами.
